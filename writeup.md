# What I Cut and Why

I intentionally kept the course focused on the minimum set of concepts needed to reach the capstone within roughly 90 minutes. I excluded full LLM API integration, streaming, provider-specific structured output features, Pydantic, advanced JSON Schema features, asynchronous processing, production observability, and sophisticated retry strategies such as exponential backoff. Those topics are useful in real systems, but including them would have made the course broader without directly helping the learner complete the required parse → validate → repair → revalidate pipeline. I also kept the learner-facing build offline by using a deterministic model stub instead of requiring an API key. That reduces setup risk and makes the build reproducible for review. The main goal was to preserve a clear progression: first build reliable parsing and schema validation, then reuse that exact artifact to add automated repair and bounded retries. I prioritized artifact continuity and runnable build-alongs over breadth.

# Where the Course Is Weakest

The weakest part of the course is the simulated model behavior used in the repair loop. The learner-facing build uses a deterministic `send_to_model()` stub so the project can run offline and produce reproducible output. This is useful for review, but it does not expose the learner to the full variety of malformed or inconsistent responses produced by a real LLM. In production, repair prompts may fail repeatedly, produce new schema violations, or return semantically incorrect data that still passes structural validation. The course also uses a deliberately simple JSON extraction heuristic for prose-wrapped responses, which is sufficient for the examples but is not intended as a production-grade parser. With more time, I would add a larger fixture set containing several failure categories and compare repair success across them. I would also include an optional live-provider mode while keeping the default offline path unchanged.
